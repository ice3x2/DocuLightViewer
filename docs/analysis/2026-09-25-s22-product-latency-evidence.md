# S22 product Electron responsiveness evidence

Issue [#45](https://github.com/ice3x2/DocuLightViewer/issues/45) is governed by `REL-DOC-007`, `IR-APP-013` AC-13, `FR-DOC-019`, and `IR-APP-010`. The active target is `0.11.0-w2`; `IR-APP-013` is `Stability=evolving` and `FR-DOC-019` is `Stability=stable`. This is S22 acceptance evidence, not a claim that either entire requirement is verified.

The process-cold run used an unpacked Windows x64 `DocuLight.exe` built by electron-builder (`--win --x64 --dir`) on B: with `win.signAndEditExecutable=false` because the account could not extract the signing tool's Darwin symlinks. The application reported `app.isPackaged=true`, profile `default`, and the isolated B: user-data directory. The test inspected the owned PID and full command line before cleanup. The raw artifact binds SHA-256 of both the executable (`1b91b1776eb5ad29756a10da223b4bb9fd5ffd6a7acaea8d6e19d83fbe4021fb`) and app.asar (`d8fb91c64f6481d4918a266d53eafb539066c3d247f6944a495e814ad4955376`). The package includes the unpacked better-sqlite3 native module; the real save and search operations completed. The package was not signed or installer-tested by this gate.

The document input is the exact deterministic Markdown fixture from the prior S22 worker checkpoint: 10,484,650 UTF-8 bytes, SHA-256 `98ef6b7bcb96965ba5a455d040b864dfc88a1c3b90e044e65c21043f3783d5b6`. It contains frontmatter, headings, fenced JavaScript, Korean and English text, and links. The second revision is 10,484,699 bytes, SHA-256 `2bfff4a19d7ae5b22c5d4089b378310e37fe37ee336f8d59e23d4614ead486b1`. B: supports the product's atomic hard-link publication; D: did not.

After a separate warm-up save reached its worker terminal event, the large document entered the product's opened-Markdown save and owner path. Worker job ID and chunk progress gated every sample. The 50 status requests traversed private IPC, the actual Settings renderer and preload, and `indexing:get-status`. The 25 focus requests used normal `update_markdown` with foreground focus, and the 25 close requests used normal `close_viewer`; each had an observer armed before the request and waited for the Electron `focus` or `closed` completion event. A post-request owner snapshot proved the same job remained active for every one of the 100 samples. The second revision was cancelled through the Settings renderer/preload `indexing:cancel-job` route while its owner job was active. The raw, immutable [source-hash-bound samples](./2026-09-25-s22-product-4f52d186f02e8e2f8e3fe73b11453ad48c60d684538347fbfe74a985921dc53d-47636-samples.json) contain every request, post marker, Electron-main tick, and gap; tested source hash: `4f52d186f02e8e2f8e3fe73b11453ad48c60d684538347fbfe74a985921dc53d`.

Every category uses nearest-rank percentiles. Settings cancel took 1.98 ms against its 1000 ms limit. An Electron-main timer supplied 7,989 ordered ticks from active worker start through the completed terminal event. The 7,990 measured gaps include the final interval after the last tick; their maximum was 40.93 ms against the 250 ms limit, and their sum was 126,555.71 ms. The active interval was 126,554.62 ms; the final latency sample ended at 126,271.80 ms. Save time (2,948.60 ms), indexed query time (68.38 ms), and prior committed query time after cancel (43.82 ms) are observations without new SLA limits. All numeric limits passed in a single packaged run; there was no minimum-of-retries selection.

The post-exit, read-only [integrity snapshot](./2026-09-29-s22-packaged-4f52d186-integrity.json) shows that both the external source and published store copy retain the cancelled revision checksum. The source ledger holds desired revision 2, completed revision 1, and dirty=1 for the same document ID; it records one completed job and one cancelled job, with a queued retry after graceful exit. The committed keyword row still has source revision 1 and the original fixture checksum. Its prior marker is present in one search segment, and the cancelled marker is absent. Both SQLite databases returned `quick_check(1)=ok`.

The same packaged session recorded both owner SQLite opens on worker thread 1 (`openCount=2`). Product main reported zero writable opens and no source ledger allocation before and after the 100 samples; its SQLite open-call counter remained 3. Its keyword read-only flag was `null` because that main connection had not been opened at the audit points. The post-exit read-only integrity check was outside the measured interval. The earlier [development-runtime S22 sample](./2026-09-25-s22-product-357a4d2d9c9cebf69d918fd5d7709395016ba88ab1b1db4d0e0de17caf3043a7-130512-samples.json) remains a separate historical observation; it measured its heartbeat in the Node harness and is not packaged AC-13 evidence.

Test-first REDs preceded the test-only probes: missing Electron-main heartbeat (`33447c82...`, exit 1, assertion 5), missing normal-request event observer (`d04fbebe...`, exit 1, assertion 7), missing same-session owner audit (`37fb09e1...`, exit 1, assertion 4), and missing packaged runtime identity (`bdad00b3...`, exit 1, assertion 1). The earlier direct-viewer RED (`8a6467b7...`) remains historical. The final command, with `DOCULIGHT_R3_PACKAGED_EXE` set to the unpacked executable and `TEMP`/`TMP` on B:, was `node test/r3/run-electron.cjs --scenario s22-product`; it exited 0 with 294 assertions. Windows x64, Node v24.16.0, Electron 33.4.11 and its ABI 130 native module were used. The harness launched child processes with hidden windows. No product scheduling change was needed.
