# Settings Freeze Hotfix Implementation Plan

## 1. Objective

배포판에서 Settings 진입 직후 Electron main process와 Windows UI가 함께 멈추는 회귀를 제거한다. 핵심은 상태 조회 비용을 전체 `index_jobs` 행 수와 무관하게 제한하고, renderer와 worker의 상태 갱신을 단일·비중첩 주기로 통제하는 것이다.

## 2. Incident Baseline

- 설치 DB: 약 195 MiB, documents 3,606개, chunks 46,615개, index_jobs 3,606개.
- SQL 원본 조회: 약 7~22 ms.
- `getIndexJobs({})` 전체 행 변환·redaction: 약 1.1~1.4 s, 호출당 RSS 약 34 MiB 증가, payload 약 2.64 MiB.
- Settings active poll: 500 ms마다 indexing status와 embedding status를 호출하고, embedding status는 별도 3 s interval도 실행.
- worker status monitor: 50 ms마다 status를 보내 main process에서 동기 SQLite job update 수행.
- 결과: polling 주기보다 상태 조회가 느려 IPC backlog와 main-process starvation이 누적됨.

## 6. Definition of Done

1. embedding progress status가 `getIndexJobs({})` 또는 전체 job redaction을 호출하지 않는다.
2. 10,000개 이상의 synthetic job에서도 aggregate status가 행 개수에 비례하는 JS 객체/문자열을 만들지 않는다.
3. Settings의 embedding status 요청은 최대 한 개만 in-flight이며 별도 global interval이 없다.
4. active indexing 상태는 500 ms cadence를 유지하되 이전 요청과 겹치지 않는다.
5. worker의 timer와 per-file rebuild event를 합친 nonterminal durable write가 500 ms에 1회를 넘지 않고 terminal/cancel 상태는 즉시 기록된다.
6. startup recovery는 파일 내용을 검증 후 queue에 보관하지 않고 worker가 처리 직전에 다시 읽는다.
7. 신규 실행형 성능/동시성 테스트가 표준 `test:wave2`와 플랫폼별 `test:release-regression` gate에 포함된다.
8. 관련 contract, Wave 1, Wave 2 및 worker contract/benchmark가 통과한다.
9. 독립 sub-agent 리뷰의 blocker/important 지적을 해결하거나 근거와 함께 명시적으로 기각한다.

## 7. Scope Boundaries

- MCP tool surface, locale text, Settings visible controls, source document content는 변경하지 않는다.
- 설치된 사용자 DB를 테스트 대상으로 쓰거나 변형하지 않는다. 모든 성능 검증은 temp DB/corpus에서 실행한다.
- 이번 hotfix에서 job history retention 정책이나 schema version 증가는 도입하지 않는다. aggregate index는 `CREATE INDEX IF NOT EXISTS`로 기존 schema와 호환한다.
- full rebuild의 모든 문서 재queue 의미는 유지한다. semantic 활성 여부만으로 derived indexing을 건너뛰지 않는다.
- producer job 생성 자체의 pagination/batching은 별도 요구사항으로 남기되, startup에서 문서 본문 전체를 queue에 보관하는 메모리 증폭은 이번 hotfix에서 제거한다.
