# Architecture — Bounded Settings Status Pipeline

## 1. Current Failure Path

```text
Settings 500 ms timer
  -> getEmbeddingModelStatus IPC
    -> SearchEngine.getSemanticIndexingProgress()
      -> SourceLedgerStore.getIndexJobs({})
        -> SELECT * for every historical job
        -> per-row public conversion + recursive redaction
        -> multi-megabyte IPC response preparation
```

동시에 worker가 50 ms마다 status를 전송하고 controller가 동일 main thread에서 SQLite `UPDATE index_jobs`를 실행한다. 읽기·redaction·쓰기 작업이 모두 Electron main event loop에 집중된다.

## 2. Target Flow

```text
Settings adaptive timeout (500 ms active / 3000 ms idle)
  -> single-flight indexing status IPC
  -> single-flight embedding status IPC
       -> SearchEngine.getSemanticIndexingProgress()
          -> SourceLedgerStore.getSemanticIndexingProgress()
             -> indexed aggregate SQL (one summary row + bounded phase)

Worker status producers (timer + per-file rebuild events)
  -> latest-status coalescer (500 ms, terminal/cancel flush)
  -> controller latest status
  -> one durable job update per heartbeat
  -> terminal status remains immediate
```

## 3. Component Responsibilities

| Component | 책임 | 금지 사항 |
| --- | --- | --- |
| `SourceLedgerStore` | active `index_document` job의 count/sum/state/phase를 SQL에서 집계 | 전체 row 반환, path/diagnostic redaction |
| `SearchEngine` | ledger aggregate를 embedding status payload 형식으로 정규화 | `getIndexJobs({})` fallback으로 전체 조회 |
| Settings renderer | adaptive timeout과 두 IPC의 single-flight 보장 | 독립 `setInterval`, overlapping request |
| search index worker | timer와 per-file event를 500 ms latest status로 coalesce, terminal/cancel 즉시 전송 | 50 ms 또는 파일별 무제한 write amplification |
| controller | 기존 terminal durability와 public redaction 유지 | 완료/실패 상태 지연 또는 유실 |

## 4. Data Contract

`SourceLedgerStore.getSemanticIndexingProgress()`는 다음 bounded object를 반환하거나 active job이 없으면 `null`을 반환한다.

```javascript
{
  state: 'queued' | 'indexing',
  phase: string | null,
  progressCurrent: number,
  progressTotal: number,
  pendingCount: number
}
```

집계 대상은 `job_type = 'index_document' AND status IN ('queued', 'indexing')`로 한정한다. `progress_total <= 0`인 job은 기존 의미와 동일하게 total 1로 계산한다. phase는 indexing job을 queued보다 우선하고, 동일 상태에서는 최신 update를 선택한다.

## 5. SQLite Design

```sql
CREATE INDEX IF NOT EXISTS idx_index_jobs_type_status_updated
  ON index_jobs(job_type, status, updated_at DESC, job_id);
```

집계 쿼리는 `COUNT`, `SUM`, `MAX(CASE...)`만 반환한다. phase 선택은 동일 predicate에 `ORDER BY CASE status ... , updated_at DESC, job_id LIMIT 1`을 적용한다. 반환 행 수는 항상 최대 2개이다. 이는 JS 결과 cardinality를 O(1)로 제한하지만 SQL scan 비용 자체가 active job 수와 완전히 무관하다는 뜻은 아니다. `EXPLAIN QUERY PLAN`으로 predicate index 사용을 검증한다.

## 6. Performance Budgets

| Signal | Budget |
| --- | --- |
| aggregate result row count | 최대 2 |
| JS result cardinality | O(1) |
| 100,000 terminal/unrelated + active synthetic jobs status query | 250 ms 이하(일반 개발 PC, warm DB) |
| renderer embedding in-flight requests | 최대 1 |
| renderer adaptive timers | 최대 1, failure 후에도 재예약 |
| active poll cadence | 500 ms |
| worker nonterminal status emission | 500 ms당 최대 1, latest status 보존 |
| REL-DOC-007 status/cancel p95 | 1000 ms 이하 |

시간 threshold는 regression detector이며 제품 SLA의 대체가 아니다. 구조 검증(`getIndexJobs` 미호출, index 존재, bounded SQL)을 함께 사용해 flaky timing 단독 판정을 피한다.

## 7. Failure and Recovery

- aggregate SQL 실패: `SearchEngine.getSemanticIndexingProgress()`는 기존과 같이 `null`을 반환하여 Settings 전체 로드를 실패시키지 않는다.
- embedding status IPC 실패: renderer는 localized unreachable 상태를 표시하고 다음 adaptive poll에서 재시도한다.
- worker status read 실패: heartbeat event는 null-safe fallback status를 보내며 terminal event 처리는 기존 경로를 유지한다.
- schema index 생성 실패: ledger initialize가 기존 recovery 흐름으로 실패하며 조용히 partial schema로 계속하지 않는다.
- startup recovery: 본문 hash 검증 후 content reference를 queue에 남기지 않는다. worker가 실제 처리할 때 UTF-8 본문을 lazy load한다.

## 8. Security and Privacy

aggregate 결과는 path, diagnostic JSON, source root, userData를 포함하지 않는다. 따라서 기존 전체 row redaction보다 노출 면적과 CPU 비용을 함께 줄인다. public Settings status의 기존 path redaction 흐름은 변경하지 않는다.
