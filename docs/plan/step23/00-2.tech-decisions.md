# Step 23: Document Type System - Technical Decisions

## ADR-001: DOC_TYPES 상수 위치

**상태**: 채택
**결정**: `frontmatter.js`에 `DOC_TYPES` 객체 정의 및 CJS export
**대안**:
- (A) 별도 `doc-types.js` 파일 → 파일 증가, 단순 상수에 과도
- (B) 각 MCP 서버에 인라인 → 중복, 동기화 문제
**근거**: frontmatter.js는 이미 MCP 서버 양쪽 + index.js에서 require하는 공유 모듈

## ADR-002: Renderer에서 DOC_TYPES 접근

**상태**: 채택
**결정**: `viewer.js`에 `DOC_TYPE_DISPLAY` 인라인 매핑 (아이콘+라벨키만)
**대안**:
- (A) preload.js를 통해 main→renderer IPC 전달 → 과도한 설계
- (B) 별도 JSON 파일 → 빌드 복잡도 증가
**근거**: 10개 정적 매핑이며 변경 빈도 극히 낮음. severity도 동일 패턴(CSS 클래스명 인라인)

## ADR-003: docType 유효성 검증

**상태**: 채택
**결정**: MCP 서버 레벨에서 Zod enum / JSON Schema enum으로 검증
**근거**: 잘못된 타입은 입력 시점에서 거부. frontmatter.js는 받은 값을 그대로 저장.

## ADR-004: 기존 문서 하위호환

**상태**: 채택
**결정**: docType이 frontmatter에 없는 기존 문서는 metabox에서 docType 행 미표시
**근거**: 기존 저장 문서에 소급 적용하지 않음. 검색 필터에서도 docType 필터 미지정 시 모든 문서 반환.

## ADR-005: {type} 토큰 vs {docType} 토큰

**상태**: 채택
**결정**: 서브디렉토리 포맷에서 `{type}` 사용 (사용자 요구사항)
**대안**: `{docType}` — 필드명과 일치하나 길어짐
**근거**: 사용자가 명시적으로 `{type}` 요청. `{severity}`도 필드명 그대로 사용하는 기존 패턴과 일관.

## 외부 라이브러리

**추가 없음**. 모든 기능은 기존 코드 확장으로 구현.
