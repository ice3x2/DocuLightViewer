# Phase 7: 성능 고도화 (선택적)

## Phase 7: 성능 고도화 — 선택적 렌더러 및 메인 프로세스 최적화 (6건)

### 목표

Phase 1~6의 안정성/정확성 개선을 완료한 후 추가로 적용하는 성능 최적화 항목이다. 사이드바 증분 렌더링, 포트 발견 루프 제한, mousemove rAF 가드, IndexedDB 단일 핸들, BM25 Worker thread 이전을 통해 렌더러 응답성과 메모리 효율을 개선한다.

> **선택적 Phase**: 안정성·정확성에는 영향을 주지 않는다. 성능 프로파일링 결과에 따라 우선순위를 조정할 수 있다.

**포함 항목 (IMPL ID 기준)**:
- IMPL-010 (H-6): 사이드바 증분 렌더링 (`container.innerHTML` 대신 diff 업데이트)
- IMPL-019 (MEDIUM port): 포트 발견 루프 범위 제한 (base ± 50)
- IMPL-020 (MEDIUM mousemove): `rafPending` 가드 추가
- IMPL-021 (MEDIUM IndexedDB): 단일 DB 핸들 재사용
- IMPL-022 (MEDIUM TOC): updateTocHighlight IntersectionObserver 전환
- IMPL-015 (MEDIUM BM25 Worker): BM25 rebuild를 Worker thread로 이전 (선택적)

## 기존 코드 재사용 힌트

### IMPL-010: 사이드바 증분 렌더링
- 현재 `buildTreeHTML(tree)` → `container.innerHTML = html` 패턴이 사용 중이다.
- 증분 렌더링의 핵심: 동일 `path` 기준으로 DOM 노드를 키-값 매핑하여 변경된 노드만 교체.
- 접근법 1 (간단): **data-path 기준 DOM 재사용**
  ```javascript
  // 기존 노드를 path 기준으로 맵으로 수집
  const existingNodes = new Map();
  container.querySelectorAll('[data-path]').forEach(el => {
    existingNodes.set(el.dataset.path, el);
  });
  // 새 트리와 비교: 변경된 항목만 교체, 없어진 항목 제거, 새 항목 추가
  ```
- 접근법 2 (복잡): Virtual DOM diff — 오버엔지니어링 가능성 높음. 접근법 1로 충분.
- 이름 토글(IMPL-010의 주요 트리거) 시에는 `data-path`는 동일하고 표시 텍스트만 변경된다 — 텍스트 노드만 업데이트하면 됨.
- 사이드바 검색 종료(exitSearchMode) 시에는 필터 해제로 트리 전체가 다시 표시되어야 한다.

### IMPL-019: 포트 발견 루프 제한
- `mcp-http.mjs`에서 포트 바인딩 실패 시 `port++`로 다음 포트를 시도하는 루프.
- 현재 루프 종료 조건이 없거나 65535까지 무한 반복 가능.
- 수정: `const MAX_PORT_TRIES = 100;` 상수 정의, base 포트 ± 50 범위(또는 0~MAX_PORT_TRIES 카운터).
  ```javascript
  const BASE_PORT = store.get('mcpPort', 52580);
  const MAX_TRIES = 100;
  for (let i = 0; i < MAX_TRIES; i++) {
    const port = BASE_PORT + i;
    try {
      await tryBind(server, port);
      return port; // 성공
    } catch (e) {
      if (e.code !== 'EADDRINUSE') throw e;
    }
  }
  throw new Error(`포트 ${BASE_PORT}~${BASE_PORT + MAX_TRIES - 1} 범위에서 사용 가능한 포트 없음`);
  ```

### IMPL-020: mousemove rafPending 가드
- `viewer.js`의 사이드바 리사이즈 또는 툴팁 관련 `mousemove` 리스너:
  ```javascript
  // 현재 패턴 (비효율적)
  container.addEventListener('mousemove', (e) => {
    requestAnimationFrame(() => { /* DOM 조작 */ });
  });
  ```
- rAF 누적 가드 패턴:
  ```javascript
  let rafPending = false;
  container.addEventListener('mousemove', (e) => {
    if (rafPending) return;
    rafPending = true;
    requestAnimationFrame(() => {
      rafPending = false;
      /* DOM 조작 */
    });
  });
  ```
- mousemove 리스너가 여러 개라면 각각에 독립적인 `rafPending` 변수 사용.

### IMPL-021: IndexedDB 단일 핸들 재사용
- `viewer.js`에서 IndexedDB를 사용하는 경우(예: 스크롤 위치 저장, 검색 히스토리 등) `indexedDB.open()`이 호출될 때마다 새 연결을 여는 패턴을 찾는다.
- 모듈 레벨에 `let _db = null;` 변수를 두고, 첫 접근 시 `open()` 후 `_db`에 저장.
- 이후 모든 접근은 `_db`를 재사용:
  ```javascript
  async function getDB() {
    if (_db) return _db;
    _db = await openDB('doculight', 1, { /* upgrade */ });
    return _db;
  }
  ```
- `idb` 라이브러리를 사용하지 않고 순수 IndexedDB API를 사용하는 경우 Promise 래퍼 패턴:
  ```javascript
  async function getDB() {
    if (_db) return _db;
    _db = await new Promise((resolve, reject) => {
      const req = indexedDB.open('doculight-settings', 1);
      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
      req.onupgradeneeded = (e) => { /* 스키마 초기화 */ };
    });
    return _db;
  }
  ```

### IMPL-022: updateTocHighlight IntersectionObserver 전환
- `viewer.js`의 `updateTocHighlight` 함수(lines 1913-1938)가 스크롤 이벤트마다 모든 heading의 `offsetTop`을 읽는 패턴.
- `offsetTop` 읽기는 layout thrashing(강제 레이아웃)을 유발한다.
- 대신 `IntersectionObserver`를 사용하면 브라우저가 자체적으로 요소 가시성을 추적하므로 매 프레임 layout 계산 없이 동작한다.
- 주의: 문서 재렌더링 시 heading DOM 노드가 교체되므로 observer를 `disconnect()`하고 새 heading들을 다시 `observe()`해야 한다.
- `rootMargin: '0px 0px -80% 0px'`은 화면 상단 20% 영역에 진입한 heading을 "현재 섹션"으로 판단한다 — 기존 `offsetTop` 기반 로직의 뷰포트 상단 임계값과 동일한 의도.

### IMPL-015: BM25 rebuild Worker thread (선택적, 난이도 높음)
- `search-engine.js`의 `rebuild()` CPU-bound 작업을 `worker_threads` 모듈로 이전.
- Worker thread에서는 `wink-bm25-text-search` 재설치가 필요하며, serialized 형태로 결과를 메인 스레드에 전달해야 한다.
- wink-bm25는 `engine.exportJSON()` / `engine.importJSON()` API를 제공한다 — rebuild 결과를 JSON으로 직렬화하여 메인 스레드에 전달 가능.
- 주의: Worker thread에서 `electron-store`, `ipcMain` 등 Electron API 사용 불가. 순수 데이터 처리만 Worker에서 수행.
- Phase 5의 IMPL-042(rebuildPromise 방어)와 연동: Worker에서 rebuild 중 메인 스레드 search는 rebuildPromise를 await.
- **구현 복잡도가 매우 높으므로 다른 IMPL이 모두 완료된 후 마지막에 구현한다.**

## 언어+버전 주의사항

- **IMPL-010 DOM API**: `querySelectorAll('[data-path]')`는 모든 브라우저/Electron에서 지원. `data-*` 속성은 DOMPurify가 `USE_PROFILES: {html: true}` 옵션에서 제거하지만, 사이드바 DOM은 DOMPurify를 거치지 않으므로 안전.
- **IMPL-019 ESM**: `mcp-http.mjs`는 ESM. `const`로 상수 선언, `import`로 의존성 로드. for...of 루프 또는 for 루프 모두 사용 가능.
- **IMPL-021 IndexedDB**: Electron renderer 프로세스에서 IndexedDB는 Chromium 기반으로 정상 동작. `sandbox: true`에서도 IndexedDB 접근 가능.
- **IMPL-022 IntersectionObserver**: Electron 33(Chromium 기반)에서 완전 지원. `rootMargin`은 CSS margin 문법을 따른다. `threshold: 0`은 1px만 보여도 콜백 호출.
- **IMPL-015 Worker thread**: Electron 33은 `worker_threads`를 지원한다. Worker 파일 경로를 `__dirname` 기준으로 지정. 패키징 시 `extraResources` 또는 `files` 설정 확인.
- **IMPL-015 wink-bm25 importJSON**: `importJSON` 후 `definePrepTasks([tokenize])` 재설정이 필요하다. importJSON은 인덱스 데이터만 복원하고 prep tasks는 복원하지 않음.

## LLM 코딩 주의사항

- **IMPL-010 복잡도 주의**: 증분 렌더링은 과도한 최적화가 되기 쉽다. 요구사항은 "전체 createElement + addEventListener 재실행 없음"이다. Virtual DOM 라이브러리 도입 금지. `data-path` 기준 단순 diff로 충분.
- **IMPL-010 이벤트 리스너 재사용**: 기존 DOM 노드를 재사용할 때 클릭 리스너가 이미 부착되어 있다면 중복 등록하지 않는다. 노드를 새로 만들 때만 리스너를 등록하는 패턴.
- **IMPL-021 Promise 재사용**: `_dbPromise = null`로 초기화된 상태에서 getDB()를 동시에 2번 호출하면 2개의 open()이 실행될 수 있다. `_dbPromise`에 Promise 자체를 저장하여 재사용(`if (!_dbPromise) _dbPromise = new Promise(...)`)하면 이를 방지.
- **IMPL-022 Observer 재등록**: 문서 재렌더링 시 기존 observer를 `disconnect()` 없이 새 heading을 `observe()`하면 이전 (이미 제거된) DOM 노드들도 계속 관찰된다. 재렌더링 진입 시 반드시 `headingObserver.disconnect()` 후 재등록.
- **IMPL-015 Electron 패키징**: Worker 파일이 asar에 포함될 경우 `__dirname` 경로가 변경된다. `require.resolve`나 `app.getAppPath()` 기반으로 Worker 경로를 계산하거나, asar 외부 extraResources로 분리.
- **Phase 7 전체**: 이 Phase의 모든 항목은 기능 변경이 아닌 성능 개선이다. 기존 동작을 유지하면서 최적화하는 것이 원칙이다. 성능 측정 전후를 비교하여 실제 개선이 있는지 확인한다.
