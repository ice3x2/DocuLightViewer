# Phase 6: 레이스 컨디션 강화

## Phase 6: 레이스 컨디션 강화 — 병렬 MCP 호출 및 동시 창 조작 안정화 (6건)

### 목표

동일 windowName에 대한 동시 생성 요청, 병렬 open/update MCP 호출, 파일 워처-IPC 경쟁, 원자적 파일 쓰기, PDF 내보내기 동시 진입 등 Node.js 싱글 스레드 `async/await` 환경에서 발생하는 레이스 컨디션을 EventEmitter 기반 대기 및 Promise 직렬화 패턴으로 안전하게 처리한다.

**포함 항목 (IMPL ID 기준)**:
- IMPL-011 (H-7): `_pendingNames` 폴링 → EventEmitter 기반 대기
- IMPL-039 (R-1): named window 동시 생성 뮤텍스
- IMPL-040 (R-2): open/update_markdown 동일 windowId 직렬화
- IMPL-041 (R-3): 파일 워처 콜백과 IPC의 `lastRenderedContent` 경쟁 방어
- IMPL-043 (R-5): `mcp-save.js` mkdir/writeFile 원자적 쓰기 (임시파일 → rename)
- IMPL-044 (R-6): `isExporting` 플래그 체크-설정 원자화

## 기존 코드 재사용 힌트

### IMPL-011: _pendingNames 폴링 → EventEmitter
- 현재 `_pendingNames = new Map<windowName, Promise>` 또는 Set 형태로 폴링을 사용 중.
- 50ms 폴링 루프 (`while (_pendingNames.has(name)) await sleep(50)`) 패턴을 제거하고 EventEmitter 기반으로 전환.
- Node.js 내장 `EventEmitter` 사용. CJS: `const { EventEmitter } = require('events');`
- `_nameEmitter = new EventEmitter()` 모듈 레벨 인스턴스 1개 생성.
- pending 이름 해소 시: `_nameEmitter.emit(windowName, windowId)` 방출.
- 대기 측: `await new Promise((resolve, reject) => { const timer = setTimeout(() => { _nameEmitter.removeListener(windowName, resolve); reject(new Error('timeout')); }, 5000); _nameEmitter.once(windowName, (id) => { clearTimeout(timer); resolve(id); }); })`
- **5초 타임아웃** 동작은 유지 필수.

### IMPL-039: createWindow 뮤텍스
- `_windowNameLock = new Map<windowName, Promise>` 를 추가.
- `createWindow(params)` 진입 시 동일 windowName에 대한 기존 Promise가 있으면 대기 후 실행.
- Promise 체인 패턴:
  ```javascript
  async function createWindowSafe(params) {
    const { windowName } = params;
    if (!windowName) return createWindow(params); // 이름 없는 창은 뮤텍스 불필요
    const prev = _windowNameLock.get(windowName) || Promise.resolve();
    let resolve;
    const next = prev.then(async () => {
      const result = await createWindow(params);
      return result;
    }).finally(() => {
      if (_windowNameLock.get(windowName) === next) {
        _windowNameLock.delete(windowName);
      }
    });
    _windowNameLock.set(windowName, next);
    return next;
  }
  ```

### IMPL-040: open/update 동일 windowId 직렬화
- `index.js`에서 `open_markdown` + `update_markdown` 핸들러에 per-windowName 직렬화 큐 추가.
- Map 기반 직렬화 큐:
  ```javascript
  const _windowOpQueue = new Map(); // windowName → Promise

  function enqueueWindowOp(windowName, fn) {
    if (!windowName) return fn(); // 이름 없는 창은 큐 불필요
    const prev = _windowOpQueue.get(windowName) || Promise.resolve();
    const next = prev.then(fn).finally(() => {
      if (_windowOpQueue.get(windowName) === next) {
        _windowOpQueue.delete(windowName);
      }
    });
    _windowOpQueue.set(windowName, next);
    return next;
  }
  ```
- `open_markdown` 핸들러: `return enqueueWindowOp(params.windowName, () => handleOpenMarkdown(params))`
- `update_markdown` 핸들러: `return enqueueWindowOp(params.windowName, () => handleUpdateMarkdown(params))`

### IMPL-041: 파일 워처-IPC lastRenderedContent 경쟁
- `window-manager.js`에서 `lastRenderedContent` 필드를 직접 읽고 쓰는 두 경로가 있다:
  1. 파일 워처 콜백: 파일 변경 감지 → 파일 읽기 → `lastRenderedContent` 업데이트 → 렌더러에 전송
  2. MCP IPC 핸들러: 새 content → `lastRenderedContent` 업데이트 → 렌더러에 전송
- Node.js 싱글 스레드에서 실제 동시 실행은 없지만, `async/await` yield 포인트(파일 읽기 await) 동안 다른 microtask가 실행될 수 있음.
- 간단한 방어: WindowEntry에 `_contentUpdatePending = false` 플래그를 추가하고, 워처 콜백이 파일을 읽는 동안 IPC 업데이트가 들어오면 플래그를 설정하여 워처의 오래된 데이터가 덮어쓰지 않도록 함.
- 또는 버전 카운터(monotonic counter) 패턴: 각 업데이트마다 버전을 증가, 워처 콜백이 파일 읽기를 시작한 버전과 완료 시 현재 버전이 다르면 결과를 버림.

### IMPL-043: mcp-save.js 원자적 쓰기
- 현재 패턴: `await fs.mkdir(dir) → await fs.writeFile(finalPath, content)`
- 원자적 쓰기 패턴:
  ```javascript
  const tmpPath = finalPath + '.tmp.' + Date.now();
  await fs.writeFile(tmpPath, content, 'utf8');
  await fs.rename(tmpPath, finalPath);
  ```
- `fs.rename()`은 같은 파일시스템 내에서 원자적 연산이다(POSIX 보장, Windows NTFS도 지원).
- `os.tmpdir()`에 쓰는 것은 다른 드라이브일 수 있어 rename이 실패할 수 있으므로 같은 디렉토리에 `.tmp` 파일을 만든다.
- `fs.rename` 실패 시 임시 파일 정리: `catch { await fs.unlink(tmpPath).catch(() => {}); throw err; }`

### IMPL-044: isExporting 원자화
- `index.js`의 PDF 내보내기 진입:
  ```javascript
  if (isExporting) return { error: '이미 내보내기 중입니다' };
  isExporting = true;
  // ... export logic ...
  isExporting = false;
  ```
- 현재 코드가 `if (isExporting)` 체크와 `isExporting = true` 설정 사이에 `await`가 있으면 race 발생 가능.
- 수정: `await` 이전에 즉시 `isExporting = true`로 설정한다.
  ```javascript
  if (isExporting) return { error: '이미 내보내기 중입니다' };
  isExporting = true; // check와 set 사이에 await 없이 즉시 설정
  try {
    // ... async export logic ...
  } finally {
    isExporting = false;
  }
  ```
- `try/finally` 패턴으로 에러 발생 시에도 플래그가 반드시 해제됨을 보장.

## 코드 중복 주의

- IMPL-039의 `_windowNameLock`과 IMPL-040의 `_windowOpQueue`는 서로 다른 계층의 직렬화를 담당한다. `_windowNameLock`은 창 생성(createWindow) 레벨, `_windowOpQueue`는 MCP 요청(open/update) 레벨이다. 혼용하지 않는다.
- IMPL-011의 `_nameEmitter`와 IMPL-039의 `_windowNameLock`은 모두 window-manager.js에 있지만 목적이 다르다. `_nameEmitter`는 pending 창 ID를 기다리는 용도, `_windowNameLock`은 동시 createWindow 직렬화 용도.
- IMPL-043의 임시 파일명에 `Date.now()` 외에 `process.pid` 또는 `crypto.randomBytes(4).toString('hex')`를 추가하면 동일 밀리초 내 충돌을 방지할 수 있다.

## 언어+버전 주의사항

- **Node.js 20 EventEmitter**: `EventEmitter.setMaxListeners(0)` 또는 충분한 최대 리스너 수를 설정해야 한다. 동일 windowName에 대해 동시 요청이 많을 경우 MaxListenersExceededWarning이 발생할 수 있다. `.once()`를 사용하므로 누적 문제는 없지만 동시에 N개가 등록될 수 있다.
- **CJS (window-manager.js, index.js, mcp-save.js)**: `require('events').EventEmitter`, `require('os')`, `require('fs').promises` 모두 CJS에서 정상 동작.
- **fs.rename 원자성**: Windows NTFS에서 `fs.rename()`은 동일 볼륨 내에서 원자적이다. 다른 볼륨으로의 rename은 실패한다 (`EXDEV` 에러). `tmpPath`와 `finalPath`가 같은 디렉토리에 있으면 동일 볼륨이 보장된다.
- **Promise 체인 메모리**: `_windowNameLock`과 `_windowOpQueue`에 쌓인 Promise 체인은 완료 후 `finally`에서 삭제되어야 한다. 삭제하지 않으면 Map이 계속 증가한다.
- **Electron 33**: `ipcMain` 핸들러(`handle`/`on`)는 동기적으로 등록되지만 핸들러 자체가 async이므로 병렬 호출이 가능하다. 직렬화 큐가 반드시 필요한 이유.

## LLM 코딩 주의사항

- **IMPL-011과 IMPL-039 연관성**: _pendingNames 폴링 제거(IMPL-011)와 createWindow 뮤텍스(IMPL-039)는 같은 문제(동시 창 생성)의 두 레이어다. IMPL-011을 먼저 구현하고 IMPL-039로 보완한다. 두 패턴이 충돌하지 않도록 설계한다.
- **IMPL-040 windowName null 처리**: `open_markdown` 호출 시 `windowName`이 없는 경우가 더 흔하다. 이 경우 큐를 우회하여 직접 처리해야 성능 저하가 없다.
- **IMPL-041 버전 카운터**: 단순 숫자 카운터면 충분하다. 카운터가 Number.MAX_SAFE_INTEGER를 초과하면 reset되는 경우를 고려해야 하지만 실용적으로는 발생하지 않는다.
- **IMPL-043 tmpPath 충돌**: 동일 프로세스에서 같은 밀리초에 같은 파일에 두 번 쓸 경우 tmpPath가 충돌한다. `Date.now() + process.pid + Math.random().toString(36)` 조합으로 충분히 고유성 확보.
- **IMPL-044 try/finally 필수**: PDF 내보내기 중 오류가 발생했을 때 `isExporting`이 true로 고정되면 이후 모든 내보내기가 차단된다. `try { ... } finally { isExporting = false; }` 구조를 반드시 사용.

## 테스트 시나리오

### IMPL-011: EventEmitter 대기
- Given: 동일 windowName "test"로 동시에 2개의 MCP open_markdown 요청
  When: 첫 번째 요청이 창을 생성하는 동안 두 번째 요청이 들어옴
  Then: 두 번째 요청은 첫 번째 창 생성 완료 후 기존 창에 upsert됨 (새 창 미생성)

### IMPL-039: createWindow 뮤텍스
- Given: 동일 windowName으로 10ms 내 3회 동시 createWindow 호출
  When: 모든 호출 완료
  Then: 창이 정확히 1개 생성됨, 교착 상태 없음

### IMPL-040: open/update 직렬화
- Given: 동일 windowName에 open_markdown + update_markdown 동시 병렬 호출
  When: 두 요청 완료
  Then: 최종 창 내용이 마지막 update 내용과 일치 (중간 상태로 덮어쓰지 않음)

### IMPL-041: 파일 워처-IPC 경쟁
- Given: 파일 워처가 파일을 읽는 중(await) MCP update_markdown 호출로 lastRenderedContent가 업데이트됨
  When: 파일 워처 읽기 완료
  Then: 워처의 오래된 파일 내용이 최신 MCP 업데이트를 덮어쓰지 않음

### IMPL-043: 원자적 쓰기
- Given: 동일 경로에 두 개의 saveMcpFile 호출 동시 실행
  When: 양쪽 완료
  Then: 저장된 파일이 한 쪽의 완전한 내용을 가짐 (두 내용 혼합 없음)

### IMPL-044: isExporting 원자화
- Given: PDF 내보내기 중 두 번째 내보내기 요청
  When: 두 번째 요청 처리
  Then: "이미 내보내기 중" 에러 반환, 첫 번째 내보내기는 정상 완료
- Given: PDF 내보내기 중 에러 발생
  When: 내보내기 핸들러 종료
  Then: `isExporting`이 false로 복원되어 다음 내보내기 가능
