## 1. Scope Overview

이 문서는 DocuLight 제품 수준의 아키텍처와 cross-cutting 제약을 정의한다. Electron 보안 baseline, 메인 프로세스(CJS)와 MCP 서버(ESM)의 프로세스 모델 분리, 벤더링된 렌더러 라이브러리 정책, electron-builder 패키징, esbuild 기반 MCP 번들 파이프라인을 다룬다.

## 2. Scope Boundaries

### In Scope

- Electron 보안 모델 baseline (contextIsolation, nodeIntegration, sandbox, CSP)
- 메인 프로세스 CJS vs MCP ESM 프로세스 모델 분리
- 빌드 및 패키징 (electron-builder Windows/macOS/Linux 산출물)
- MCP stdio 서버 번들링 (esbuild)
- 벤더링된 렌더러 라이브러리(marked, DOMPurify, highlight.js, mermaid) 정책
- 외부 링크 개방 정책 (http/https 한정)

### Out of Scope

- 기능별 동작 (각 feature scope: APP, WIN, TREE, MCP, DOC, RENDER)
- 렌더링 파이프라인 세부 (RENDER)
- MCP 도구 핸들러 로직 (MCP)

## 3. Assumptions and Constraints

- Electron 33.x 런타임을 대상으로 한다.
- MCP 번들은 Node 20 타깃으로 빌드한다.
- 패키징은 Windows(NSIS+Portable), macOS(zip), Linux(AppImage+deb)를 대상으로 한다.

#### Requirement

시스템은 빌드된 DocuLight 실행 파일이 `--mcp-stdio` 인자로 실행될 때 외부 Node 설치 없이 MCP stdio server mode로 동작하도록 해야 한다. 이 mode는 기존 HTTP MCP와 병용되어야 하며, 기존 source stdio MCP, HTTP MCP, generated bundle과 동일한 8-tool 계약을 유지하고, 실제 저장/검색/창 동작은 Electron main process의 기존 IPC, WindowManager, Store, SearchEngine 경계를 통해 수행해야 한다.

#### Rationale

기존 `package.json` bin과 source stdio MCP는 개발/소스 환경의 CLI 기반 MCP를 제공하지만, Electron installer가 설치본 CLI entrypoint를 보장하지는 않는다. 사용자는 HTTP MCP와 병용되는 CLI 기반 MCP가 빌드된 앱에서도 동작하기를 요구했으므로, 설치본 실행 파일 자체가 검증 가능한 stdio MCP entrypoint를 제공하고 package smoke가 이를 실제 MCP client로 검증해야 한다.

#### Acceptance Criteria

- [x] AC-1: `DocuLight --mcp-stdio` 또는 플랫폼별 동등 실행은 BrowserWindow, tray, Settings window, HTTP MCP server를 이 CLI 프로세스 안에서 시작하지 않고 MCP stdio transport를 시작한다.
- [x] AC-2: CLI stdio mode의 stdout에는 newline-delimited MCP JSON-RPC 메시지 외의 문자열을 쓰지 않고, 모든 로그와 diagnostics는 stderr 또는 MCP error envelope로만 전달한다.
- [x] AC-3: CLI stdio mode의 `tools/list`는 `open_markdown`, `update_markdown`, `close_viewer`, `list_viewers`, `save_document`, `search_documents`, `search_projects`, `smart_search`의 정확한 8개 tool name set을 source stdio, HTTP, generated bundle과 동일하게 노출한다.
- [x] AC-4: CLI stdio mode는 `save_markdown`, `store_document`, `remember_document` 같은 alias 도구와 rebuild, clear, retry, cancel, status, import, reconciliation, model-change 계열 MCP indexing control 도구를 노출하지 않는다.
- [x] AC-5: CLI stdio mode는 `DOCULIGHT_MCP_IPC_PATH` 명시 endpoint를 최우선으로 사용하고, `DOCULIGHT_MCP_PROFILE`, `DOCULIGHT_PROFILE`, `DOCULIGHT_RUNTIME_PROFILE` 기반 default/dev profile 선택을 기존 runtime profile resolver와 동일하게 적용한다.
- [x] AC-6: 기본 profile에서 대상 app IPC server가 없을 때 CLI stdio mode가 installed app을 자동 실행하는 경우, 자식 앱은 일반 app mode로 실행되어야 하며 `--mcp-stdio`, `ELECTRON_RUN_AS_NODE`, stdio-only 환경이 자식 앱에 전파되어 recursive CLI launch를 만들지 않아야 한다.
- [x] AC-7: dev profile 또는 explicit IPC endpoint 선택 시 CLI stdio mode는 packaged app을 자동 실행하지 않고, 의도한 endpoint가 없다는 redacted MCP error를 반환한다.
- [x] AC-8: CLI stdio mode는 `better-sqlite3`, `hnswlib-node`, embedding provider, search index worker native module을 직접 load하지 않고 기존 Electron main process service 계층과 IPC를 통해 저장/검색 동작을 수행한다.
- [x] AC-9: package smoke는 빌드 산출물의 `DocuLight --mcp-stdio`를 실제 MCP stdio client로 실행하여 `initialize`, `notifications/initialized`, `tools/list`, `save_document`, `smart_search`, invalid `save_document`, invalid `smart_search` pathPrefix validation을 검증한다.
- [x] AC-10: package smoke는 같은 packaged app 인스턴스에서 HTTP MCP `tools/list`와 CLI stdio `tools/list`가 동일한 8-tool surface를 제공하고, 한 transport로 저장한 unique marker가 다른 transport의 `search_documents` 또는 `smart_search`로 검색되는지 검증한다.
- [x] AC-11: package smoke artifact는 stdout purity, stderr diagnostics, selected runtime profile, redacted IPC endpoint class, cross-transport marker identity, and no-indexing-control evidence를 raw absolute path나 credential echo 없이 기록한다.
- [x] AC-12: 기존 `npm run mcp`, source stdio MCP, `bundle:mcp`, `mcp-server.bundle.mjs` package parity, `npm run start`, `npm run dev`, normal packaged app startup behavior는 이 CLI entrypoint 추가로 회귀하지 않는다.

### SEC-ARCH-005 — Remote image mediation and safe media download

| Field | Value |
| --- | --- |
| Type | security |

| Related Docs | docs/research/mermaid-image-dedicated-viewer-requirements-2026-07-09.md, docs/research/mermaid-image-dedicated-viewer-implementation-plan-2026-07-09.md |

#### Requirement

시스템은 media viewer에서 원격 이미지를 표시하거나 다운로드할 때 renderer가 직접 원격 리소스를 가져오게 하지 않고 main process 중계를 통해 안전하게 가져와야 한다. 원격 이미지 중계는 protocol allowlist, redirect 재검증, private network 차단, credential/header 제거, MIME 검증, timeout, byte size cap, filename sanitization, renderer-visible error redaction을 적용해야 한다.

#### Rationale

원격 이미지 지원은 문서 표시 기능이지만, 임의 URL fetch를 renderer나 main process에 무제한 허용하면 SSRF, credential leakage, local network probing, unsafe filename write 위험이 생긴다. 기존 로컬 이미지 IPC처럼 main process가 명시 정책으로 중계해야 보안 경계를 유지할 수 있다.

#### Acceptance Criteria

- [x] AC-1: remote image fetch는 `http:`와 `https:` URL만 허용하고 다른 protocol은 fetch 전에 거부한다.
- [x] AC-2: redirect를 follow하는 경우 각 redirect hop과 최종 URL에 protocol allowlist와 private-network 차단 정책을 다시 적용한다.
- [x] AC-3: URL username/password credential은 거부하거나 제거하고, fetch request에는 cookie, referrer, Authorization header를 보내지 않는다.
- [x] AC-4: localhost, loopback, link-local, private IPv4/IPv6 대역은 기본 차단한다.
- [x] AC-5: response `Content-Type`은 image MIME type만 허용하고 non-image response는 renderer에 redacted error로 보고한다.
- [x] AC-6: fetch에는 timeout과 maximum byte size cap을 적용하고, 초과 시 partial data를 버린 뒤 redacted error를 반환한다.
- [x] AC-7: download filename은 `Content-Disposition`, URL basename, MIME-derived extension, fallback name 순으로 결정하되 traversal, path separator, control character, OS reserved name, extension spoofing을 sanitization한다.
- [x] AC-8: renderer-visible response와 logs에는 raw remote credential, absolute local path, unsafe network error detail을 포함하지 않는다.
- [x] AC-9: media viewer HTML CSP는 remote script, remote style, remote font를 허용하지 않고 media asset 표시에는 main-process가 제공한 safe data/blob payload만 사용한다.
- [x] AC-10: remote image 보안 정책은 local/data URL image 및 Mermaid SVG download 경로를 회귀시키지 않는다.
